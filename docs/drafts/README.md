# 要件叩き台の運用

要求を実装可能な要件へ言語化するための「叩き台」を、このディレクトリに置きます。
設計・実装より先に要件定義を固めるための作業場であり、ここにある内容は現在仕様の正ではありません（正は `docs/product/PRD.md`・`docs/features/`・`docs/changes/`・`docs/design/`）。

## 位置づけ
- 合意前の仮説を書いてよい唯一の場所。仮説には必ず【仮】を付け、合意できたら外す
- 要件の言語化（目的・対象ユーザー・スコープ・受入条件）に限定する。画面レイアウト・API・テーブル定義などの設計には踏み込まない
- 設計への波及に気づいたら「論点」に書き留めるに留め、叩き台が「叩き中」の間は、そのテーマについて `docs/design/` 等の設計書を先回りして更新しない

## 命名規則
`<YYYY-MM-DD>_<テーマ>.md` のように、作成日と短いテーマ名で作成します（例: `2026-07-08_受注管理.md`。同日同テーマが複数ある場合は `2026-07-08_受注管理-2.md` のように `-2` 等を付す）。
反映後に削除する一時ファイルのため、機能ID等の連番は採番しません。
叩き台の一覧は、このディレクトリ直下のファイル一覧を正とし、このファイルには持ちません。

## ライフサイクル
| ステータス | 状態 |
|---|---|
| 叩き中 | 壁打ちで【仮】と論点を潰している段階 |
| 合意済み | 主要な【仮】が外れ、反映先が確定した段階 |
| （反映後） | 正ドキュメントへ反映し、叩き台ファイルは削除する。経緯は Git 履歴と `docs/project/log/` が担う |

## 進め方
1. `_template.md` をコピーして叩き台を作成する（/draft コマンド、または requirements スキルの「叩き台ファースト」）
2. 壁打ちで論点を確認し、合意できた記述から【仮】を外す。解消した論点は行ごと消す
3. 主要な【仮】が外れたらステータスを「合意済み」にし、反映先（新規機能なら `docs/features/`、改修なら `docs/changes/`、プロダクト全体なら `docs/product/PRD.md`、共通要求なら `docs/requirements/`）へ反映する
4. 解消しなかった論点は反映先の「未確定事項」へ移す。反映が終わった叩き台ファイルは削除する
