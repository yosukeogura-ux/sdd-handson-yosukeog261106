# 改修の運用

既存機能の改修、障害対応、仕様変更は、このディレクトリに改修単位で記録します。

## 命名規則
`CHG-001_改修名/` のように、改修IDと短い改修名でディレクトリを作成します。
改修IDは既存の最大番号+1で採番し、欠番は詰めません（ADR と同一の規則）。
改修の一覧は、このディレクトリ直下のフォルダ一覧を正とし、このファイルには持ちません。

## 1改修あたりの標準構成
```text
CHG-001_改修名/
├── request.md              # 改修依頼・背景・目的
├── current.md              # 現在の仕様・現行動作
├── after.md                # 改修後の仕様
├── impact.md               # 影響範囲調査
├── implementation-plan.md  # 実装方針・変更対象
└── test.md                 # テスト観点（実行結果は docs/test/ に記録）
```

## 作業順序
1. `request.md` で依頼内容・目的・対象機能（機能ID）を整理する
2. `current.md` で現行仕様・現行コードの動作を確認する
3. `after.md` で変更後仕様を定義する
4. `impact.md` で影響範囲を調査する
5. `implementation-plan.md` で実装方針を決める
6. 対象機能が `docs/features/` に存在する場合は、実装に着手する前に変更後仕様を反映する（必須）
7. 実装前に `test.md` へテスト観点を整理し、それを基にテストケース一覧を `docs/test/` の対象機能ファイルへ作成・追記して、ユーザーの承認を得る
8. 実装後、`docs/test/` に実行結果を記録する（必要に応じて `test.md` も更新）

改修では、いきなり実装せず、必ず `current.md` と `impact.md` を作成してから着手します。

## 運用ルール
- 新規か改修かの判定は CLAUDE.md「新規開発と改修の進め方」の判定規則に従う（迷ったら改修）
- `docs/features/` への変更後仕様の反映は実装と同じブランチで行い、同一 PR でマージする（main 上で仕様と実装の一致を保つため、反映だけを先行して main へマージしない）。実装中に仕様の手戻りが生じた場合は `after.md` と `docs/features/` の両方を修正する
- 対象機能が `docs/features/` に未文書化で、同じ機能への改修が繰り返される場合は、機能フォルダを新設して現在仕様を集約する（バックフィル）
- `request.md` の「ステータス」を進行に合わせて更新する（受付 → 実装中 → 完了）
- 完了した改修フォルダは当時の記録（スナップショット）として残す。現在仕様の正は `docs/features/`・`docs/design/`
