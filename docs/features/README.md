# 機能仕様の運用

機能単位の「現在仕様の正」を、このディレクトリに記録します（新規・既存を問わない）。
新規開発で作成し、改修（`docs/changes/`）では実装に着手する前に変更後仕様を反映します。新規か改修かの判定は CLAUDE.md「新規開発と改修の進め方」の判定規則に従います（迷ったら改修）。

## 命名規則
`F001_機能名/` のように、機能IDと短い機能名でディレクトリを作成します。
機能IDは既存の最大番号+1で採番し、欠番は詰めません（ADR と同一の規則）。
機能の一覧は、このディレクトリ直下のフォルダ一覧と `docs/product/PRD.md` の主要機能一覧を正とし、このファイルには持ちません。

## 1機能あたりの標準構成
```text
F001_機能名/
├── requirements.md  # 要求・ユーザーストーリー・受入条件
├── spec.md          # 画面・処理・入力チェックなどの詳細仕様
├── mock/            # HTML モック（画面を持つ機能のみ。ダミーデータ・画面遷移のみ）
├── data.md          # 使用データ・テーブル影響
├── api.md           # API・外部連携がある場合の仕様
└── test.md          # テスト観点・受入確認
```

モックは合意済み仕様の一部として git 管理する。実装前にブラウザで確認してユーザーの承認を得てから、テストケース作成・実装へ進む（モックファースト）。画面構成に影響する改修（レイアウト変更・画面追加・遷移変更等）では、変更後仕様の反映と同時にモックも更新する（文言修正など軽微な変更は `docs/changes/` の `after.md` の「画面の変更点」の合意で代替してよい）。

## 作成手順
1. `_template/` をコピーする
2. ディレクトリ名を `F001_機能名` 形式に変更する
3. `requirements.md` → `spec.md` → `data.md` → `api.md` → `test.md` の順に具体化する（API・外部連携がない機能の `api.md` は「なし」と明記すればよい。既存機能・共有部品に接点がある場合は `spec.md` の「既存機能への影響」を必ず埋める）
4. 画面を持つ機能は `mock/` に HTML モックを作成し、ユーザーの承認を得る（画面を持たない機能は `spec.md` の「画面モック」に「なし」と明記し、「入出力例」を合意する）

## 既存機能のバックフィル
`docs/features/` に未文書化の既存機能へ改修が繰り返される場合は、機能フォルダを新設して現在仕様を集約する。作成後は、その機能の改修でも実装に着手する前に変更後仕様を反映する（必須）。
