# コーディング規約

## 基本原則
- **KISS / YAGNI**: 今必要なものだけを、最も単純な形で実装する。将来の拡張を見越した抽象化はしない
- **単一責任**: 関数・クラスは1つの責務に集中させる。目安: 関数50行以内、1ファイル300行以内（超えたら分割を検討）
- **DRY**: 同じロジックを3回書いたら共通化を検討する（2回までは重複を許容してよい）
- **早期リターン**: ネストを深くせず、ガード節で早期に return する
- **マジックナンバー禁止**: 意味のある定数名を付けて定義する

## 命名規則
- 関数名・API名・クラス名は、英語に統一する
- データベースのテーブル名・ビュー名・カラム名・変数名・ファイル名・ファイルパスは、対応する業務用語がある場合はローマ字表記を基本とする（例: 得意先 → `tokuisaki`）。一般的なIT用語（`id`, `status`, `flag`, `count` 等）は英語のままでよい
- 同じ業務用語には常に同じローマ字表記を使う（表記のブレを避ける）。頻出する業務用語の表記は `docs/design/data/` のテーブル定義に合わせる

| 対象 | 規則 | 例 |
|---|---|---|
| 変数・関数 | 役割が伝わる完全な単語。省略形は避ける（業務用語のカラム名・変数名はローマ字可） | `fetchUserProfile`, `tokuisaki_id`（× `fetchUsrProf`, `tks_id`） |
| 真偽値 | is / has / can / should を接頭辞に | `isActive`, `hasPermission` |
| 関数 | 動詞始まり | `createOrder`, `validateInput` |
| 定数 | 大文字スネークケース | `MAX_RETRY_COUNT` |
| クラス・型 | PascalCase の名詞 | `OrderRepository` |

ケース（camelCase / snake_case）は各言語の標準に従う。

## 型安全
- TypeScript: `strict: true` 前提。`any` 禁止（やむを得ない場合は `unknown` + 型ガード）。公開関数の戻り値型は明示する
- Python: すべての関数に型ヒントを付ける。`Any` を使う場合は理由をコメントに残す
- null / undefined の可能性は型で表現し、システム境界（入力・API応答）で検証する

## コメント
- 「何をしているか（What）」は書かない。コードで表現する
- 「なぜこの実装にしたか（Why）」だけを書く: 仕様上の制約、回避策の理由、非自明なビジネスルール
- `TODO(名前): 内容` 形式で記載し、放置しない

## フォーマット
- フォーマッタ（Prettier / Ruff 等、プロジェクト標準）の出力を正とする。手動整形しない
- lint エラーは警告も含めて解消してからコミットする
