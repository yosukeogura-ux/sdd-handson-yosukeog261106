# テスト方針

## 基本方針
- 新規ロジックにはテストを必ず書く。テストのない実装は完了とみなさない
- テストケース一覧（`docs/test/<機能名>.md`）は新規・改修を問わず**実装前に作成し、ユーザーの承認を得る**。承認を得るまで実装・テストコード作成に着手しない
- バグ修正はまず**失敗する再現テスト**を書いてから修正する
- テストピラミッド: ユニットテスト（多）> 統合テスト（中）> E2E（少・クリティカルパスのみ）
- テストケース一覧は `docs/test/<機能名>.md` に、実行結果は `docs/test/<機能名>-履歴.md` に機能ごとに記録する（規約: `.claude/rules/test-documentation.md`）

## カバレッジ基準
| 対象 | 基準 |
|---|---|
| 新規・変更コード | 80% 以上を目安 |
| ビジネスロジック・金額計算・権限判定 | 100% を目指す |
| 設定ファイル・自動生成コード・単純な委譲 | 対象外でよい |

数値達成のための無意味なテスト（アサーションなし・実装をなぞるだけ）は禁止。

## テストの書き方
- **AAA パターン**: Arrange（準備）→ Act（実行）→ Assert（検証）を明確に分ける
- **1テスト1観点**: 1つのテストで検証する振る舞いは1つだけ
- **命名**: 「対象_条件_期待結果」が伝わる名前にする
- **網羅順序**: 正常系 → 境界値 → 異常系の順に書く
- **独立性**: テスト間で状態を共有しない。実行順序に依存させない
- **決定論的**: 時刻・乱数・外部APIは固定化（fake / freeze）し、flaky なテストを作らない

## モック方針
- モック対象は**境界のみ**: 外部API・DB・時刻・ファイルシステム・メッセージング
- 自作のビジネスロジックはモックしない（モックだらけのテストは実装の写しになる）
- モックの戻り値は実際のレスポンス形式に忠実にする

## 実行タイミング（段階的に範囲を広げる）
| タイミング | 実行範囲 |
|---|---|
| テスト作成・修正の直後 | 作成・修正したテスト（green を確認するまで完了としない） |
| 実装ステップごと・コミット前 | 変更に関連するテスト |
| バグ修正後 | 全テスト（回帰確認） |
| コード・セキュリティレビューの [must] 解消後 | 全テスト（回帰確認） |
| push / PR 前・リリース前 | 全テスト（+ lint・型チェック） |

- テストはフックで**自動実行しない**。実行時間が不定で、編集や停止のたびに走ると開発を阻害するため、上記タイミングで Claude が明示的に実行する（Stop フック `check-consistency.py` が検査するのはテスト・テスト記録・データモデル文書の更新の「有無」のみで、テストの実行はしない）
- テスト実行コマンドは `docs/operations/env.md` の「コマンド」を参照
