# 実装の進め方

## 手順
1. **現在地の確認**: `docs/project/progress.md` を確認する。経緯が必要な場合のみ `docs/project/log/` の直近ファイルを読む
2. **作業種別の確認**: 新規開発なら `docs/features/<対象機能>/`、改修なら `docs/changes/<対象改修>/` を読む
3. **共通仕様・設計の確認**: `docs/product/PRD.md`、`docs/requirements/`、`docs/design/`、`docs/operations/env.md` を読む
4. **既存パターンの調査**: 同種の機能がどう実装されているかを先に調べ、命名・構成・イディオムを踏襲する
5. **改修時の影響範囲確認**: `docs/changes/<対象改修>/impact.md` がない場合は、実装前に作成する
6. **改修時の仕様反映の確認**: 対象機能が `docs/features/` に存在する場合は、変更後仕様が反映済みであることを確認する。未反映ならここで反映してから先へ進む（必須。実装と同じブランチで更新し、同一 PR に含める）
7. **タスク分解**: 「1画面・1正常系」を目安とした縦切りスライス（それ単体でユーザーが画面確認できる単位）に分割する
8. **モック承認の確認**: 画面を持つ機能は、承認済みの HTML モックが `docs/features/<対象機能>/mock/` にあることを確認する。未作成・未承認なら実装に入らず設計（モック作成・承認）に戻る（画面を持たない機能は `spec.md` の「入出力例」、画面構成に影響しない軽微な改修は `after.md` の「画面の変更点」の合意を確認する）
9. **テストケース承認の確認**: 承認済みのテストケース一覧（`docs/test/<機能名>.md`）があることを確認する。未作成・未承認の場合は一覧を作成し、ユーザーの承認を得てから実装に着手する
10. **テストファースト**: 失敗するテストを書き、実行して失敗を確認する → 最小実装で通す → リファクタする
11. **スライスごとに画面確認**: スライスの実装ができたら、次のスライスへ進む前にユーザーに画面確認を依頼する（ブラウザプレビュー等で実際に見てもらう）。NG はそのスライス内で修正してから先へ進む
12. **ステップごとに検証**: lint・型チェック・関連テストを都度実行する。壊れたまま次へ進まない。全スライス完了後は「/review（コード・セキュリティレビュー）→ [must] 解消 → 全テストで回帰確認 → 最終全体確認レビュー → PR」の順に進む
13. **ドキュメント同期**: 仕様・計算ロジック・テーブル定義に影響があれば `docs/features/`・`docs/changes/`・`docs/design/`・`docs/design/data/` を同時更新する（画面に変更が及んだ場合は `mock/` も実態に合わせて更新する）。利用者に見える変更は `CHANGELOG.md` の Unreleased に追記する
14. **記録**: 区切りごとに `progress.md` を上書き更新する（セッションログはユーザーの「ログを記録して」による手動起動時のみ追記する）

## 原則
- **動く最小から始める**: 骨格 → 正常系 → エラー処理 → 境界条件の順に肉付けする
- **画面確認を最後にまとめない**: スライスごとにユーザーに見せて認識ズレを早期に検出する。全機能を実装し終えてから初めて画面を見せるのは禁止
- **1変更1目的**: 機能追加と無関係なリファクタを混ぜない
- **ライブラリ追加は許可制**: 標準ライブラリ・既存依存で実現できないかを先に検討する
- **改修は差分管理**: 現行仕様・変更後仕様・影響範囲を明確にしてから実装する
- **エラーを握り潰さない**: 例外は適切に処理するか上位へ伝播させる。空の catch は禁止

## 完了条件
- [ ] 受け入れ基準を満たしている
- [ ] 新規ロジックにテストがあり、関連テストが green
- [ ] 承認済みのテストケース一覧が `docs/test/<機能名>.md` にあり、実行結果を `docs/test/<機能名>-履歴.md` に記録済み
- [ ] lint・型チェックがエラーなし
- [ ] docs/ の関連ドキュメントを更新済み
- [ ] progress.md を更新済み
