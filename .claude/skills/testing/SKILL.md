# テスト作成の型

前提: `.claude/rules/testing-policy.md`（カバレッジ基準・モック方針）と `.claude/rules/test-documentation.md`（テスト記録規約）に従う。

## 手順
1. **既存テストの調査**: フレームワーク・ディレクトリ構成・命名・ヘルパの使い方を確認し、必ず踏襲する
2. **観点の洗い出し**: 対象の振る舞いを「正常系 → 境界値 → 異常系」の順で列挙する
3. **テストケース一覧の確認**: 実装前に承認されたテストケース一覧（`docs/test/<機能名>.md`）と観点を突き合わせる（書式: `docs/test/README.md`）。一覧が未作成・未承認の場合や、洗い出しでケースの追加・変更が生じた場合は、一覧を作成・更新してユーザーの承認を得てから先へ進む
4. **AAA で書く**: Arrange（準備）/ Act（実行）/ Assert（検証）を明確に分ける。1テスト1観点
5. **実行して green を確認**: 書いただけで完了にしない。実行結果を確認・報告する
6. **結果の記録**: 実行結果を `docs/test/<機能名>-履歴.md` に追記し、一覧（`docs/test/<機能名>.md`）の「最新結果」列を ○/×/− に更新する。**失敗が残る場合は履歴ファイルに失敗の記録（事象・原因・修正方法）を書き、ユーザーに必ず報告する**

## テストの型
```text
テスト名: 「<対象>_<条件>_<期待結果>」が伝わる名前
  Arrange: 入力・前提状態・モックを準備する
  Act:     対象を1回だけ実行する
  Assert:  期待する振る舞いを検証する
```
- 同型のケースが3つ以上あればテーブル駆動（parametrize / test.each）にまとめる
- 時刻・乱数・UUID は固定化する。実時間 sleep での待機は禁止（flaky テストの温床）

## バグ修正時の鉄則
1. まず**失敗する再現テスト**を書く（バグが再現することを確認する）
2. 修正する
3. テストが green になることを確認する（このテストが回帰テストとして残る）

## モック方針（testing-policy の要点）
- モック対象は境界のみ: 外部 API・DB・時刻・ファイルシステム
- 自作のビジネスロジックはモックしない
- モックの戻り値は実際のレスポンス形式に忠実にする

## アンチパターン
- 実装の内部構造（プライベート関数・呼び出し回数）への過度な依存 → 公開された振る舞いを検証する
- アサーションのないテスト、出力を目視するだけのテスト
- テスト間の状態共有・実行順序への依存
- カバレッジの数値だけを目的とした無意味なテスト
