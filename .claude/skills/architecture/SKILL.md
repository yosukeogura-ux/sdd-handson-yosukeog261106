# アーキテクチャ設計・ADR

## 設計判断の観点（優先順）
1. **データの流れ**: どこで生まれ、どこで検証され、どこに保存されるか
2. **責務の境界**: 各モジュールの責務を1文で言えるか。言えなければ分割・統合を見直す
3. **依存の方向**: 依存は安定したもの（ドメイン・抽象）へ向ける。循環依存は禁止
4. **変更のしやすさ**: 変更頻度が異なるものは分離し、同時に変わるものは近くに置く
5. **YAGNI**: 現時点で不要な拡張ポイント・抽象化は作らない

## 技術選定の基準
| 観点 | 確認すること |
|---|---|
| 実績・メンテ状況 | 最終リリース日、Issue 対応状況、利用実績 |
| 既存スタックとの整合 | 既に同種のライブラリがないか（重複導入禁止） |
| 学習コスト | チームが保守できるか |
| ライセンス | 商用利用可否（MIT / Apache-2.0 は可、GPL 系は要相談） |
| 撤退しやすさ | 置き換え時の影響範囲が局所化できるか |

※ ライブラリ追加はユーザー許可制（動作規定「振る舞いの制限」）。選定比較をユーザーに提示して判断を仰ぐ。

## ADR の書き方
重要な技術判断（フレームワーク選定・データストア変更・認証方式など）は `docs/adr/ADR-XXX-短い判断内容.md` に記録する（動作規定「振る舞いの制限」。XXX は前ゼロ付き3桁の連番で、既存の最大番号+1を採番。例: `ADR-001-セッションログ自動保存.md`。1判断1ファイル）。
決定した全体構成・レイヤ構成・依存方向は `docs/design/architecture.md` に、ディレクトリ構造・実装規約への影響は `docs/design/tech.md` に反映（上書き）する。

```markdown
# ADR-XXX: <決定内容の要約>

日付: YYYY-MM-DD

## ステータス
承認 | 提案中 | 廃止（ADR-XXX で置換）

## コンテキスト
（なぜこの判断が必要になったか。制約・前提）

## 決定
（何をどうするか）

## 検討した代替案
（案と却下理由）

## 結果
（この決定で得るもの・失うもの・受け入れる制約）
```

- 決定を覆す場合は既存 ADR を書き換えず、新しい ADR で置き換える（判断の履歴を残す）

## アンチパターン
- 使うかどうか分からない汎用化・プラグイン機構
- 流行・新しさだけを理由にした技術選定
- ADR なしの重要判断（後から「なぜこうなっているか」が失われる）
