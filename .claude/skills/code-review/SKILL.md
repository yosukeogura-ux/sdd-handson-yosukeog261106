# コードレビュー観点チェックリスト

## 進め方
1. 対象差分を把握する（`git diff` / PR）。先に変更の**目的**を理解する
2. 差分のファイル種別から適用する観点を選ぶ（下記「差分種別と適用観点」）
3. 該当するチェックリストを重要度順に確認する。差分に該当しない観点は「対象外」として飛ばす
4. 指摘は severity を付けて `file:line` 形式で報告する
5. 良い実装は良いと明記する（指摘だけのレビューにしない）

## 差分種別と適用観点

差分に含まれるファイルの種別で適用する観点を決める。種別が混在する場合は、該当する観点をすべて適用する。

| 差分の種別 | 例 | 適用する観点 |
|---|---|---|
| ソースコード | `src/`・`app/`・`lib/` 配下 | ①〜⑥ すべて |
| テストコード | `tests/`・`*.test.*` | ① 正しさ・③ テスト・⑤ 可読性 |
| スクリプト・フック・CI | `.claude/hooks/`・CI 定義 | ① 正しさ・② セキュリティ・⑤ 可読性 |
| 設定・依存関係 | `settings.json`・`.gitignore`・パッケージ定義 | ② セキュリティ・変更の影響範囲 |
| 仕様・設計ドキュメント | `docs/product/`・`docs/requirements/`・`docs/features/`・`docs/changes/`・`docs/design/`・`docs/adr/` | ドキュメント差分の観点 ＋ 仕様・設計差分の観点 |
| 動作規定・開発ルール | `CLAUDE.md`・`.claude/` 配下の `*.md`（rules・skills・agents・commands） | ドキュメント差分の観点 ＋ 仕様・設計差分の観点 |
| その他ドキュメント | 上記以外の `*.md`（README・`docs/project/`・`docs/test/` 等） | ドキュメント差分の観点のみ |

## チェックリスト

### ① 正しさ（最優先）
- [ ] 仕様・受け入れ基準どおりに動くか
- [ ] 境界値・空・null・0件・重複データでも壊れないか
- [ ] エラー処理: 例外の握り潰し・空 catch がないか。失敗時に状態は整合するか
- [ ] 並行実行・二重実行で壊れないか（該当する場合）

### ② セキュリティ（.claude/rules/security.md 準拠）
- [ ] 秘密情報のハードコード・ログ出力がないか
- [ ] SQL インジェクション・XSS・パストラバーサル等の禁止パターンがないか
- [ ] 入力検証と認可チェック（所有者確認）があるか

### ③ テスト（.claude/rules/testing-policy.md 準拠）
- [ ] 新規ロジックにテストがあるか
- [ ] 異常系・境界値がテストされているか
- [ ] テストが実装の写しになっていないか（振る舞いを検証しているか）
- [ ] テストケース一覧が `docs/test/<機能名>.md` に、実行結果（○/×）が `docs/test/<機能名>-履歴.md` に記録されているか（.claude/rules/test-documentation.md 準拠）

### ④ 設計
- [ ] 単一責任・依存の方向が守られているか
- [ ] 既存のパターン・命名と整合しているか
- [ ] 不要な抽象化・過剰な汎用化がないか（YAGNI）

### ⑤ 可読性
- [ ] 命名から役割が分かるか
- [ ] コメントが Why を説明しているか（What の説明コメントは不要）
- [ ] 深いネスト・長すぎる関数がないか

### ⑥ 性能
- [ ] N+1 クエリ、ループ内の I/O・重い処理がないか
- [ ] 不要な再計算・過剰なメモリ確保がないか（計測なしの過剰最適化も指摘対象）

## ドキュメント差分の観点

.md にはコード観点（①〜⑥）を適用しない。差分が .md のみの場合は code-reviewer サブエージェントを起動せず、レビュー実施者が直接確認する（コードと混在する場合は code-reviewer がコード観点と併せて確認する）。

- [ ] 記録先が動作規定「ドキュメントの役割分担」に合っているか（例: 経緯が progress.md に書かれていないか）
- [ ] 追記式ドキュメント（CHANGELOG.md・docs/adr/・docs/test/ の履歴ファイル `<機能名>-履歴.md`・docs/project/log/ のセッション要約ログ）以外に変更履歴・経緯の記載を追加していないか（動作規定「振る舞いの制限」）
- [ ] 実装・他のドキュメントと矛盾する記載がないか
- [ ] 参照しているファイルパス・リンクが実在するか
- [ ] 秘密情報（実キー・接続文字列等）が含まれていないか

## 仕様・設計差分の観点

仕様・設計ドキュメントと動作規定・開発ルールの差分には、ドキュメント差分の観点に**加えて**以下を確認する。どちらも実装・Claude の動作の上流であり、誤り・曖昧さがそのまま波及するため、記録系ドキュメントより厳密に見る。

- [ ] 上流・関連文書と整合しているか
  - 仕様・設計: docs/features/・docs/changes/・docs/design/ の変更が PRD.md や docs/requirements/ と矛盾していないか。機能仕様・改修差分・共通設計 ⇔ docs/design/data/ のテーブル定義・制約（テーブルごとの `<テーブル名>.md` ⇔ overview.md の一覧・リレーション） ⇔ tech.md の規約
  - 動作規定: CLAUDE.md ⇔ rules ⇔ スキル・エージェント・コマンドの間で、役割分担・手順・参照先（見出し名・ファイルパス）が矛盾していないか
- [ ] 既存の実装・テストとの乖離が生じるか
  - 仕様・設計: 乖離が生じる場合、実装追随の予定が残課題（progress.md / セッションログ）として認識されているか
  - 動作規定: フック実装（`.claude/hooks/`）の分類・判定と食い違っていないか
- [ ] 改修（docs/changes/）の実装差分に、対象機能の docs/features/（存在する場合）への変更後仕様の反映が含まれているか（反映は実装前・同一 PR が原則）
- [ ] 読み手（実装者・Claude）が迷う曖昧さがないか（未定義の用語・境界条件や異常系の欠落・「〜など」で濁した記述・分岐の網羅漏れ）
- [ ] 後戻り困難な決定（アーキテクチャ・データモデルの重要な変更）を含む場合、ADR が作成されているか（動作規定「振る舞いの制限」）

## severity 分類
| ラベル | 意味 |
|---|---|
| [must] | マージ不可。バグ・脆弱性・データ破壊の恐れ |
| [should] | 対応推奨。設計・保守性の問題 |
| [nits] | 好みの範囲。対応は任意 |
| [ask] | 質問・意図の確認 |

## 指摘の書き方
`<severity> <file>:<line> — <問題> / <理由> / <修正案>` の形で、理由と代替案まで示す。
