# 要件定義・仕様策定（壁打ち）

## 目的
ユーザーとの対話を通じて要求を実装可能な粒度まで具体化し、PRD・機能仕様・改修差分・データモデルへ反映する。
ユーザーはこれらのドキュメントを手書きしない。Claude が対話を整理して書く。

## 反映先の使い分け
| 内容 | 反映先 | 更新方法 |
|---|---|---|
| 合意前の要求の言語化（叩き台。仮説は【仮】付き） | `docs/drafts/<日付>_<テーマ>.md` | 上書き。反映後に削除 |
| プロダクト全体の目的・スコープ・成功条件 | `docs/product/PRD.md` | 上書き |
| 全機能共通の要求・非機能要件 | `docs/requirements/` | 上書き |
| 機能単位の現在仕様（新規・既存とも。要求・仕様・受入条件） | `docs/features/<機能ID>_<機能名>/` | 上書き |
| 改修・障害対応・仕様変更の依頼・現行仕様・変更後仕様・影響範囲 | `docs/changes/<改修ID>_<改修名>/` | 上書き |
| データモデル（エンティティ・関係・制約） | `docs/design/data/` | 上書き |
| 画面・API・バッチなどの共通設計 | `docs/design/` | 上書き |
| 後戻り困難な設計判断 | `docs/adr/ADR-XXX-短い判断内容.md` | 新規ファイル |

## 叩き台ファースト（要求の言語化）
要求が断片的で言語化されていない段階では、質問から始めるのではなく、Claude がまず叩き台を書き、ユーザーはそれを添削する（ゼロから答えるより、たたく方が早い）。/draft コマンドでも起動できる。

1. `docs/drafts/_template.md` を元に `docs/drafts/<YYYY-MM-DD>_<テーマ>.md` を作成し、提示された断片を要件の形（目的・対象ユーザー・スコープ・受入条件）に言語化する
2. 仮説で埋めた箇所には必ず【仮】を付け、確認したいことは「論点」に優先度順で挙げる。`docs/drafts/` は合意前の仮説を書いてよい唯一の場所
3. 叩き台の要約と論点（1メッセージ3つまで）を提示して壁打ちし、合意できた記述から【仮】を外す。解消した論点は行ごと消す
4. 主要な【仮】が外れたらステータスを「合意済み」にし、「反映先の使い分け」に従って正ドキュメントへ反映する。解消しなかった論点は反映先の「未確定事項」へ移し、その後に叩き台ファイルを削除する
5. 叩き中は設計に踏み込まない。画面・API・データモデルへの波及に気づいたら「論点」に書き留め、要件合意後に扱う

## 壁打ちの進め方
1. **作業種別の判定**: 新規開発か、既存改修か、共通設計変更かを整理する（既存機能の仕様・受入条件に変更が生じるなら改修。迷ったら改修として扱う）
2. **材料の把握**: 提示された要件断片・既存資料を読み、現行ドキュメントとの差分を整理する
3. **プロアクティブな質問**: 「誰が・何のために・現状の何が課題か」から確認する。質問は1メッセージ3つまでに絞る。要求がまだ言語化されていない場合は、質問攻めにせず「叩き台ファースト」で始める
4. **スコープの合意**: 「やること」「やらないこと」を提示して合意を取る
5. **新規の場合**: `docs/features/_template/` を元に機能単位で requirements/spec/data/api/test を作る。画面を持つ機能は `mock/` に HTML モック（ダミーデータ・画面遷移のみ、ロジックなし）を作成し、ブラウザで確認してユーザーの承認を得る（モックファースト）。画面を持たない機能は `spec.md` の「入出力例」で入力と期待出力の具体値を合意する
6. **改修の場合**: `docs/changes/_template/` を元に request/current/after/impact/implementation-plan/test を作る。画面構成に影響する変更（レイアウト変更・画面追加・遷移変更等）は対象機能の `mock/` を更新（無ければ変更対象の画面のみ作成）して承認を得る。文言修正・軽微な項目追加はモック不要とし、`after.md` の「画面の変更点」の合意で代替する。推測で実装に入らない
7. **データモデルの整理**: DB影響がある場合は db-design スキルに従い `docs/design/data/` に反映する
8. **未確定事項の分離**: 推測で埋めず、該当ファイルの「未確定事項」に残す
9. **反映と確認**: 合意内容だけを反映先へ上書きし、ユーザーにレビューを求める

## 書き方の原則
- ドキュメントには常に現在のあるべき姿のみを書く。経緯・変更履歴は書かない
- 合意前の仮説を書いてよいのは `docs/drafts/` の叩き台のみ。仮説には必ず【仮】を付け、正ドキュメントには合意した内容だけを書く
- PRD に細かい画面項目・クラス設計を書かない。機能別詳細は `features/`、改修差分は `changes/`、技術設計は `design/` に分ける
- 受入条件のない機能要件を残さない

## アンチパターン
- 叩き台を `docs/drafts/` ではなく PRD・features・changes に直接書き始める（正の場所に未合意の仮説を混ぜない）
- 要件定義・壁打ちの段階で `CHANGELOG.md` に書く（CHANGELOG は実装完了後の記録）
- 叩き台が「叩き中」のまま設計（`docs/design/`）や実装に進む
- 新規機能の詳細をすべて PRD.md に詰め込む
- 改修で `current.md`・`impact.md` を作らずに実装する
- 画面を持つ機能で、モックの承認を得ないままテストケース作成・実装へ進む
- 改修で、変更後仕様を対象機能の `docs/features/` に反映しないまま実装に着手する
- ユーザーの回答を待たずに、推測のデータモデルや業務ルールを書く
