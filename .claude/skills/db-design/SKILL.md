# DB スキーマ設計・マイグレーション

## 命名規則
| 対象 | 規則 | 例 |
|---|---|---|
| テーブル | snake_case 複数形 | `user_orders` |
| カラム | snake_case | `total_amount` |
| 主キー | `id` | |
| 外部キー | `<参照先単数形>_id` | `user_id` |
| 日時カラム | `<動詞過去形>_at`。`created_at` / `updated_at` は全テーブル必須 | `shipped_at` |
| 真偽値 | `is_` / `has_` 接頭辞 | `is_active` |
| インデックス | `idx_<table>_<columns>` | `idx_orders_user_id` |

## 設計方針
- **第3正規形を基本**とする。パフォーマンス目的の非正規化は ADR に理由を残す
- カラムは可能な限り NOT NULL にし、意味のあるデフォルト値を持たせる
- 金額は整数（最小通貨単位）または DECIMAL。浮動小数点型は禁止
- 整合性は DB 制約（FK・UNIQUE・CHECK）で担保する。アプリコードだけに頼らない
- 論理削除か物理削除かはプロジェクトで統一し、docs/design/data/overview.md の共通方針に明記する
- **インデックス**: 外部キー・検索条件・ソートに使う列に付与する。書き込みコストとのバランスを見て、推測で乱発しない

## マイグレーション手順
1. `docs/design/data/`（全体像 `overview.md` と該当テーブルの `<テーブル名>.md`）で現行スキーマを確認する
2. 1マイグレーション = 1目的。up / down（ロールバック）を必ず両方書く
3. 稼働中システムでは**後方互換を保つ**（expand → migrate → contract の3段階）:
   - **expand**: 新カラム・新テーブルを追加（旧コードも動く状態を維持）
   - **migrate**: データ移行と両対応コードのデプロイ
   - **contract**: 旧カラムの削除は移行完了を確認してから、別マイグレーションで行う
4. カラム削除・型変更・NOT NULL 化はデータ喪失リスクがあるため、実行前にユーザーへ影響を報告して承認を得る
5. 該当テーブルの `docs/design/data/<テーブル名>.md` を同時更新する（テーブルの追加・削除・リレーション変更時は `overview.md` も。書式は `docs/design/data/README.md`。動作規定「振る舞いの制限」。Stop フックでも検査される）

## アンチパターン
- down（ロールバック）のないマイグレーション
- 1つのマイグレーションに複数目的の変更を混ぜる
- 本番データでの検証なしに大量データのテーブルへ重いマイグレーションを適用する
