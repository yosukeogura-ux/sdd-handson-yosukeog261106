# API 設計規約

## 設計手順
1. `docs/design/api.md` で全体の API 規約・命名を確認する
2. 新規機能の場合は `docs/features/<対象機能>/api.md`、改修の場合は `docs/changes/<対象改修>/after.md` と `impact.md` を確認する
3. リソースと操作を洗い出し、下記規約に沿って設計する
4. API 仕様を該当ドキュメントへ更新してから実装に着手する
5. 破壊的変更になる場合は既存クライアントへの影響を報告し、バージョニングで対応する

## REST 規約

### URL・リソース
- リソース名は複数形の名詞: `/users/{id}/orders`
- 動詞を URL に入れない。操作は HTTP メソッドで表現する
- ネストは2階層まで。それ以上はクエリパラメータかトップレベルリソースにする

### HTTP メソッドとステータスコード
| メソッド | 用途 | 成功時 |
|---|---|---|
| GET | 取得（副作用なし） | 200 |
| POST | 作成・非冪等な操作 | 201（作成）/ 200 |
| PUT | 全体置換（冪等） | 200 |
| PATCH | 部分更新 | 200 |
| DELETE | 削除（冪等） | 204 |

エラー: 400 / 401 / 403 / 404 / 409 / 422 / 500
※ 認可エラーでリソースの存在が漏れる場合は 404 を返す。

### レスポンス形式（プロジェクト内で統一）
```json
{ "data": {} }
```

```json
{ "error": { "code": "VALIDATION_ERROR", "message": "説明", "details": [] } }
```

- エラー message に内部情報を含めない
- 一覧系エンドポイントにはページネーションを付ける
- バージョニングは URL プレフィックス（`/v1/`）を基本とする

## GraphQL 補足
- スキーマファースト。スキーマ変更は API 仕様ドキュメントと同期する
- N+1 を DataLoader 等で防ぐ
- Mutation 名は「動詞 + 対象」。入力は input オブジェクトにまとめる

## アンチパターン
- エンドポイントごとにバラバラなエラーレスポンス形式
- GET での状態変更
- 内部 ID・内部構造をそのまま外部レスポンスに露出する
