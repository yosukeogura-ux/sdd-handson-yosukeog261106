# デバッグ手順（再現 → 仮説 → 検証）

## 鉄則
- **根本原因を特定するまで修正しない**。対症療法（とりあえずの try-catch、条件分岐の追加）で症状だけ消すのは禁止
- 憶測と事実を区別する。エラーメッセージ・ログ・スタックトレースの**原文**を根拠にする

## 手順
1. **再現**: 確実に再現する最小手順を確立する。再現できない場合は、発生時の入力・環境・ログを収集してから進める
2. **最小化**: 再現条件を削って問題を切り分ける（入力を減らす、コンポーネントを外す）
3. **事実の収集**: エラー全文・関連ログ・直近の変更（`git log` / `git diff`）を確認する
4. **仮説を1つ立てる**: 「〜だから〜が起きる」と説明できる形にする
5. **検証**: 仮説を確認する最小の実験を行う（ログ追加・デバッガ・単体実行・二分探索）
6. **繰り返し**: 仮説が外れたら 3〜5 を繰り返す。3回外れたら前提を疑い、より上流（入力・設定・環境）を確認する
7. **修正**: まず失敗する再現テストを書き（testing スキル）、根本原因に対する最小の修正を行う
8. **回帰確認**: 全テストを実行し、副作用がないことを確認する。実行結果は `docs/test/<機能名>-履歴.md` に追記する（テスト記録規約）
9. **記録**: 原因と対処を `docs/test/<機能名>-履歴.md` の失敗の記録（事象・原因・修正方法）として残す（同種バグの再発時に効く。テスト記録規約）。未記載なら追記し、記載済みなら「対応状況」行のみ更新する（本文は書き換えない）。調査の経緯そのものはセッションログ（`docs/project/log/`）への要約追記で残す

## 切り分けテクニック
| 状況 | 手法 |
|---|---|
| どこで壊れているか不明 | 正常な入口から二分探索でログ・ブレークポイントを入れる |
| いつから壊れたか不明 | `git bisect` / 直近のコミットを順に確認する |
| 環境によって挙動が違う | 環境変数・依存バージョン・設定ファイルの差分を比較する |
| 再現が不安定 | 並行処理・時刻依存・外部依存・テスト間の状態共有を疑う |

## 一度に1変更
検証中に複数箇所を同時に変えない。どの変更が効いたのか分からなくなり、調査が振り出しに戻る。
